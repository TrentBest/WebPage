# WebApp Runtime Architecture\n\nThe WebPage repository is the **WebApp manifestation** of The Singularity Workshop.\n\nIt is not the composition engine.\n\n## Runtime boundary\n\n```text\n                    WebPage / WebApp\n                           |\n                           | reads\n                           v\n              webapp.runtime.json\n                           |\n                           | translates\n                           v\n                  FSM_COS RuntimeManifest\n                           |\n                           | resolve\n                           v\n                MicroBundle source/repository\n                           |\n                           | materialize\n                           v\n                       MicroBundle\n                           |\n                           | Load + Arbitrate\n                           v\n                         FSM_COS\n                           |\n                           | converge\n                           v\n                    RuntimeAssembly\n                           |\n                           | manifest\n                           v\n                    Blazor presentation\n```\n\n## Ownership\n\nThe WebApp owns:\n\n- browser startup;\n- configuration-file retrieval;\n- browser-specific presentation;\n- user input and rendering;\n- the WebApp-specific source adapter while repository integration is being completed.\n\nFSM_COS owns:\n\n- manifest execution;\n- dependency traversal;\n- MicroBundle loading;\n- arbitration;\n- convergence;\n- the sealed RuntimeAssembly.\n\nThe MicroBundle domain owns the meaning of a MicroBundle. A repository owns storage and retrieval. The WebApp should not become a second composition engine.\n\n## MVP vertical slice\n\nThe current MVP proves one complete path:\n\n1. `wwwroot/runtime/webapp.runtime.json` names the runtime and requested MicroBundle IDs.\n2. `WebPageCosRuntime` translates that file into `FSM_COS.RuntimeManifest`.\n3. `WebPageMicroBundleCatalog` supplies the requested MicroBundle through `IMicroBundleCatalog`.\n4. `FsmCos.Execute()` loads and arbitrates the requested composition.\n5. `RuntimeAssembly` becomes the source for the idle Pong manifestation.\n6. The Blazor component no longer constructs Pong directly.\n\nThe in-process catalog is intentionally a **replaceable source adapter**, not the final repository architecture. The next repository step is to replace that adapter with the MicroBundleRepository/FSM_COS integration without changing the WebApp manifest or presentation contract.\n\n## Host symmetry\n\nThe same runtime contract is intended to support:\n\n```text\nWebApp          -> browser manifestation\nAnyApp          -> desktop/application manifestation\nDistributedApp  -> distributed manifestation\n```\n\nThose hosts may have completely different presentation technology while consuming the same composition model:\n\n```text\nManifest + Configuration\n          |\n          v\n      Repository\n          |\n          v\n       FSM_COS\n          |\n          v\n RuntimeAssembly\n          |\n    +-----+-----+----------------+\n    |           |                |\n  WebApp      AnyApp       DistributedApp\n```\n\nThat is the MVP pathway: **prove the interoperability in WebPage by actually consuming FSM_COS, rather than merely documenting that WebPage eventually will.**\n
